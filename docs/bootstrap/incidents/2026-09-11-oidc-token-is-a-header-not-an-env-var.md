# 2026-09-11 — OIDC トークンを環境変数から読もうとして、本番が全言語 500 になった

## 何が起きたか

7 言語の実行を Vercel Sandbox に統一 (ADR 0003) して本番へ初回デプロイした直後、
**7 言語すべてが 500 `{"error":"実行環境の認証情報がありません (サーバー設定の問題です)"}`** を返した。
ローカルからは同じ `dispatch` コードで 7/7 成功していた。

原因は認証情報の取り方。`api/execute.rs` は環境変数 `VERCEL_OIDC_TOKEN` を読んでいたが、
**Vercel は関数の実行時、OIDC トークンを環境変数ではなくリクエストヘッダ
`x-vercel-oidc-token` で渡す**。環境変数に入るのは次の 2 つの場合だけ:

- ビルド時 (`VERCEL_OIDC_TOKEN` が注入される)
- ローカル開発 (`vercel env pull` が `.env.local` に書く) ← **ここで検証していたので気づけなかった**

ドキュメント (https://vercel.com/docs/oidc) の "How OIDC token federation works" に
"In Builds" / "In Vercel Functions" / "In Local Development" と 3 つ並んでおり、
関数の節だけがヘッダである。

## なぜ問題だったか

- **ローカル検証が本番と同じコードを通していたのに、認証情報の「入口」だけが違っていた。**
  `dispatch` を直接呼ぶ疎通テスト (7 言語 × 3 ケース) はすべて緑で、
  「配信される実物を実上流に対して走らせた」という検証の強度を過信した
- 環境変数を読むコードは**本番でだけ None になる**。型も落ちず、テストも緑のまま

## 対処

- `shared::sandbox::pick_token(header, env_oidc, env_fallback)` を追加。
  優先順は **リクエストヘッダ → `VERCEL_OIDC_TOKEN` → `KNOCKS_VERCEL_TOKEN`**。
  空白だけの値は「無い」として扱う
- `api/execute.rs` の `handler` が body を消費する前にヘッダを取り出し、`dispatch` に渡す
- `tools/local_server.rs` も同じ順序でヘッダを受けるようにした
  (検証ハーネスと本番の入口を同じ形に保つ)
- 本番再デプロイ後、7 言語で 正解 → `test result: ok` / 壊したコード → 言語固有の診断を実測

## 教訓

- **「env に入る」と書いてあっても、どの実行文脈の env かを読む。**
  ビルド / 関数 / ローカルで注入方法が違うプラットフォーム変数がある
- **ローカルで実上流に繋がる検証は、認証の経路だけは本番と別物になりやすい。**
  上流 API の応答形は検証できても「トークンがどこから来るか」は検証できない。
  この種の差は**本番に出して実測するしか閉じられない** (今回もデプロイ後の実測で 3 分で判明した)
- 逆に良かった点: 文言が「認証情報がありません (サーバー設定の問題です)」だったので、
  利用者のコードの問題でないことが即座に切り分けられた (2026-09-07 の教訓が効いた)

## 継ぎ目 (どこを跨いだか)

この変更が跨いだ境界は「速くなったか」ではなく、**待つのをやめて何が壊れうるか**。

1. **後片づけの契約** — 停止が届かなかったとき、サンドボックスは誰が消すのか
2. **判定の契約** (ADR 0002 の `Outcome` 5 分類) — 順序を変えて判定が変わらないか
3. **本番環境** — ローカルで速くても本番の関数で速いとは限らない
   (関数は応答後に凍る可能性があり、投げた停止が走り切る保証はない)
4. **枠** — 停止が届かない提出が増えると Hobby の同時 10 / 作成 5,000 に効くか
5. **計測そのもの** — 1 回の計測で「速くなった」と言っていないか

## 残る穴 (正直な記録)

1. **「停止が届かない」割合は実測していない (L1-2 の本番版)**
   ローカルでは届くことを確かめたが、本番の関数が応答後にどれだけ生きるかは
   Vercel 側の都合で、こちらから観測する手段がない。届かなかったぶんは
   サンドボックス自身の `timeout` (60s) で消える (L1-3) ので、**最悪の見積もりは
   「1 提出あたり最大 60 秒 生き残る」**。同時 10 台の枠に対して、
   1 秒あたり 0.16 提出を超えて常時使われると理屈の上では詰まる。
   個人利用の規模では起きないが、混雑の文言 (`BUSY`) が出始めたらここを疑う。

2. **ばらつきは減っていない**
   同じ言語でも 1〜12 秒に散る。原因は関数のコールドスタートと region ごとの
   イメージの温まり (L3 の領域) で、L1 では触っていない。
   体感の下限を詰めるのは ② の再利用 (要 ADR)。

3. **ブラウザでの検証は未実施**
   `/api/execute` の契約 (`{language, code}` → `ExecuteResponse`) は不変で、
   フロントは 1 行も変えていないため API レベルの検証に留めた。
